==================================================
1. ATURAN UTAMA
==================================================

Jangan langsung coding.

Jangan membuat UI berdasarkan asumsi pribadi.

Jangan membuat feature baru yang tidak ada di requirement.

Jangan mengubah requirement.

Jangan mengimplementasikan backend, database, AI, risk engine, atau routing algorithm.

Sebelum implementasi, kamu harus:

1. Menemukan dan membaca seluruh dokumen requirement yang relevan.
2. Memahami hubungan antar requirement.
3. Mengidentifikasi requirement yang berkaitan dengan Flutter Mobile.
4. Melakukan audit terhadap scope implementasi.
5. Mengidentifikasi dependency dengan backend/API.
6. Mengidentifikasi bagian yang belum jelas atau berpotensi conflict.
7. Membuat implementation plan.
8. STOP dan tunggu konfirmasi sebelum melakukan perubahan kode.

3. AUDIT SCOPE FLUTTER MOBILE
==================================================

Setelah membaca dokumen, audit seluruh scope berikut:

6. Flutter Mobile
├── Foundation
├── Dynamic Safety Map
├── Destination Selection
├── Route Visualization
├── Hazard Reporting
├── Hazard Review
└── Emergency Simulation

Untuk SETIAP bagian, identifikasi:

### A. Requirement

Apa requirement yang secara eksplisit meminta feature tersebut?

### B. Screen

Screen/page apa yang diperlukan?

### C. User Flow

Bagaimana user berpindah dari satu screen/state ke screen lainnya?

### D. UI Components

Component apa saja yang diperlukan?

### E. Interaction

Apa yang dapat dilakukan user?

### F. UI State

Identifikasi state seperti:

- initial
- loading
- success
- empty
- error
- disabled
- selected
- submitting
- processing
- completed
- unavailable

Gunakan hanya state yang memang relevan dengan requirement.

### G. Data Requirements

Data apa yang harus ditampilkan oleh UI?

### H. Backend/API Dependency

Apakah UI membutuhkan:

- API endpoint
- response data
- location data
- hazard data
- route data
- simulation state
- report status
- AI result
- risk score

Jika iya, identifikasi dependency-nya.

### I. Business Logic Boundary

Tentukan dengan jelas apakah logic tersebut:

Flutter UI responsibility

ATAU

Backend/Core System responsibility.

Contoh:

Flutter:
- menampilkan hazard
- menampilkan severity
- menampilkan route
- menerima input report
- menampilkan simulation result

Backend:
- menentukan hazard severity
- AI hazard extraction
- menghitung risk
- menghitung route
- menentukan route penalty
- melakukan route recalculation
- memproses simulation logic

Jangan memindahkan backend responsibility ke Flutter hanya karena UI membutuhkannya.

==================================================
17. PRINCIPLE
==================================================

Prioritas utama:

REQUIREMENT
    ↓
AUDIT
    ↓
TRACEABILITY
    ↓
BOUNDARY
    ↓
IMPLEMENTATION PLAN
    ↓
CONFIRMATION
    ↓
IMPLEMENTATION

Bukan:

REQUIREMENT
    ↓
ASSUMPTION
    ↓
CODING

Jangan melakukan speculative implementation.

Jika requirement tidak jelas, katakan tidak jelas.

Jika API belum tersedia, katakan belum tersedia.

Jika ada conflict, laporkan.

Jika sebuah feature membutuhkan keputusan dari developer, minta konfirmasi.

Tujuan tahap ini bukan menghasilkan kode.

Tujuan tahap ini adalah memastikan bahwa ketika implementasi dimulai:

1. Scope jelas.
2. Requirement terlacak.
3. UI sesuai specification.
4. API dependency jelas.
5. Business logic boundary jelas.
6. Tidak terjadi overlap dengan backend/core system.
7. Tidak terjadi unnecessary rework.
8. Implementasi dapat dilakukan secara paralel dengan development backend.
